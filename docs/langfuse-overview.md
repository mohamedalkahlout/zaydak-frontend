**الموقع:** [https://langfuse.com](https://langfuse.com)  
**النوع:** منصة مفتوحة المصدر (MIT) لهندسة تطبيقات الـ LLM والـ Agents  
**آخر تحديث لهذا الملف:** 2026-09-19

**حالة Zaydak:** Tracing على كل أسطح الـ AI في Nest (اختياري عبر env) عبر `ai-trace.ts`. التكلفة بالدولار تظهر في Langfuse عندما يكون المزود OpenRouter ويرجع `usage.cost` (بعد إصلاح تفضيل شكل الـ usage الذي يحمل التكلفة). تقرير Admin المالي لكل متجر يقرأ من `usage_events` عبر `aiSpendByShop` — ليس من Langfuse. تنبيه يومي عند ارتفاع إنفاق متجر. قرار المقارنة: [langsmith-vs-langfuse.md](./langsmith-vs-langfuse.md). **آخر تحديث:** 2026-09-19.

## ما هي؟

Langfuse منصة **مراقبة وتقييم وتحسين** لتطبيقات الذكاء الاصطناعي (خاصة الـ LLM والـ Agents).  
فكر فيها كـ **Sentry / Datadog لكن مصمّمة للـ AI**: ما تسجّل أخطاء فقط، بل تسجّل كل خطوة في محادثة أو وكيل — البرومبت، الرد، استدعاء الأدوات، التكلفة، والزمن.

تُستخدم لـ:

1. **Observability (تتبع)** — ماذا حصل فعلاً في كل طلب؟
2. **Evaluation (تقييم)** — هل الجودة جيدة؟ وهل تراجعت بعد تغيير؟
3. **Prompt management** — إدارة البرومبتات خارج الكود مع إصدارات وrollback
4. **Experiments** — تجارب A/B على بيانات حقيقية قبل النشر

يمكن تشغيلها كـ **Cloud** (خطة مجانية محدودة) أو **Self-host** مجاناً بالكامل تحت MIT.

## المشكلة التي تحلّها

تطبيقات الـ LLM غير حتمية: نفس السؤال قد يعطي جواباً مختلفاً، والوكيل قد يستدعي أدوات كثيرة، والتكلفة تتراكم بصمت.

بدون أداة مثل Langfuse عادةً يصير عندك:

| الوضع بدونها | الوضع معها |
|---|---|
| لوجات نصية مبعثرة | Trace هرمي واضح لكل جلسة |
| "الموديل غالي" بدون رقم | تكلفة وtokens لكل طلب / مستخدم / متجر |
| تعديل برومبت في الكود وتخمين | مقارنة تجارب على نفس الـ dataset |
| شكوى مستخدم بدون سياق | فتح الـ session ورؤية كل الخطوات |

## الميزات الأساسية

### 1) Tracing (الأهم للبداية)

يسجّل لكل طلب:

- المدخلات والمخرجات (prompt / completion)
- استدعاءات الأدوات (tool calls)
- خطوات الـ retrieval إن وُجدت
- الزمن (latency) وعدد الـ tokens والتكلفة التقريبية
- ربط بـ user / session / metadata (مثل `shopId`)

الـ SDK يرسل البيانات **بشكل غير متزامن**؛ لا يبطّئ الاستجابة تقريباً.

### 2) Evaluation

طرق تقييم متعددة:

- **LLM-as-a-judge** — موديل يقيّم جودة الرد
- **Heuristics / code evaluators** — قواعد برمجية (طول، JSON صالح، عدم تسريب سر…)
- **Human review** — مراجعة بشرية وبناء golden datasets

يمكن تشغيل التقييم على بيانات الإنتاج أو أثناء التجارب.

### 3) Prompt management

فصل البرومبتات عن الكود:

- إصدارات + نشر بنقرة + rollback
- Playground لتجربة برومبت على مدخلات إنتاج حقيقية
- مقارنة موديلات جنباً إلى جنب

### 4) Datasets & Experiments

بناء مجموعة اختبارات (حالات حقيقية أو يدوية)، تشغيل تجربة بعد تغيير برومبت/موديل، ومقارنة النتائج قبل الإطلاق.

### 5) Cost & latency dashboards

لوحات ولوحات تنبيه عندما تتجاوز التكلفة أو زمن الاستجابة أو نسبة فشل الجودة حداً معيناً.

## التكاملات

تعمل مع أغلب الستاك الشائع:

- **لغات:** TypeScript / Python أصلياً، وباقي اللغات عبر OpenTelemetry
- **Frameworks:** LangChain، Vercel AI SDK، LiteLLM، CrewAI، وغيرها
- **موديلات:** OpenAI، Anthropic، Bedrock، Gemini، Mistral، Groq، vLLM…

ليست مقفلة على مزود واحد؛ التصميم مبني على OpenTelemetry لتقليل الـ lock-in.

## ماذا نستفيد منها في زايدك؟

المشروع فيه عدة أسطح AI حقيقية (Sidekick / vendor-agent، storefront assistant، negotiation، توليد وسائط، bots على WhatsApp/Telegram). Langfuse مفيدة تحديداً في:

### أ) تصحيح الوكلاء بسرعة

مثال: Sidekick يستدعي أدوات كثيرة (`import_product`، تقارير، …).  
بدل تخمين "ليش تاه؟"، تفتح الـ trace وتشوف:

- أي أداة استُدعيت وبأي args
- أي خطوة أكلت وقت/تكلفة
- هل الموديل هلوس أم الأداة رجعت خطأ

هذا يقلّل زمن الـ debug من ساعات إلى دقائق.

### ب) مراقبة التكلفة الحقيقية لكل متجر / ميزة

عندكم بالفعل منطق خطط وusage و`cost_cents`. Langfuse يكمّل بصورة تشغيلية:

- تكلفة كل محادثة Sidekick
- تكلفة negotiation replies
- مقارنة موديل أرخص مقابل جودة مقبولة
- اكتشاف متاجر أو مسارات تستهلك بشكل شاذ

### ج) تحسين الجودة بدون تخمين

- تقييم آلي: هل الرد كشف سعر الأرضية؟ هل اخترع خصماً؟
- جمع جلسات سيئة → dataset → تجربة برومبت جديد → قياس التحسن قبل النشر
- تثبيت regressions بعد كل تغيير على الـ prompts

### د) إدارة البرومبتات كمنتج

بدل برومبتات مدفونة في Nest services:

- إصدار واضح لكل برومبت (negotiation phrasing، Sidekick system prompt، …)
- rollback فوري إذا نسخة جديدة ساءت
- تعاون بين المنتج والهندسة على النص بدون deploy لكل تعديل صغير (حسب طريقة الربط)

### ه) خصوصية وامتثال

Cloud فيه مناطق EU/US وامتثال (SOC 2، ISO 27001، GDPR).  
أو **self-host** داخل بنيتكم إذا بيانات المحادثات حساسة ولا تريدونها تخرج.

## ماذا لا تحلّ؟

- ليست بديلاً عن **Sentry** لأخطاء HTTP/Prisma العادية
- ليست نظام فوترة للعملاء — الفوترة عندكم تبقى في الـ back-end / plans
- لا تغني عن اختبارات الوحدة؛ هي طبقة **مراقبة وتجارب على سلوك الـ LLM**
- تحتاج قرار واضح: ما الذي يُسجَّل؟ وما الذي يُقنَّع (PII، أرقام هواتف، عناوين)؟

## خيارات النشر

| الخيار | متى يناسب |
|---|---|
| **Langfuse Cloud — Hobby** | تجربة سريعة (حدود مجانية، ~50k observations/شهر) |
| **Cloud — مدفوع** | إنتاج بدون تشغيل بنية |
| **Self-host (Docker/K8s)** | تحكم كامل بالبيانات، تكلفة بنية فقط |

## مسار تبنّي مقترح لـ زايدك (إن قررتم)

1. **أسبوع 1 — Tracing فقط** على مسار واحد (مثلاً Sidekick أو negotiation).
2. إضافة metadata: `shopId`, `feature`, `userId` (مع masking للـ PII).
3. لوحة تكلفة + latency أسبوعية.
4. جمع 20–50 جلسة سيئة يدوياً → dataset.
5. Evaluator بسيط (قواعد أو LLM-judge) على هذا المسار.
6. لاحقاً: prompt management للبرومبتات الأكثر تغيّراً.

لا حاجة لتبنّي كل المنصة دفعة واحدة؛ أغلب الفرق تبدأ بالـ tracing فقط.

## الخلاصة

| السؤال | الجواب المختصر |
|---|---|
| ما هي؟ | منصة مفتوحة لمراقبة وتقييم وتحسين تطبيقات LLM/Agents |
| ليش مفيدة لنا؟ | Sidekick، negotiation، المساعدات والـ bots — كلها صندوق أسود بدونها |
| أكبر مكسب فوري؟ | رؤية كل خطوة + التكلفة + إصلاح سريع للجلسات الفاشلة |
| أكبر مكسب متوسط المدى؟ | تجارب برومبت/موديل مبنية على بيانات إنتاج حقيقية |
| هل نحتاجها الآن؟ | نعم إذا الـ AI في الإنتاج ويكلف/يؤثر على تجربة التاجر؛ لا إذا ما زال تجريبياً ونادراً |
