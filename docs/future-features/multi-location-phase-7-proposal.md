## 1. ما وُجد في الكود

| المفهوم | الحالة قبل هذه المرحلة |
|---|---|
| **`customerShippingCharge`** | ✅ **موجود** — `Order.delivery_fee_cents`، يُحسب خادميًا من `ShippingZone`/`ShippingRule` |
| الملغى منه | ✅ **موجود** — `Order.cancelled_delivery_fee_cents` |
| **`actualShippingCost`** | ❌ لا عمود تكلفة على `Shipment` ولا على `Order` |
| **`merchantShippingSubsidy`** | ❌ غير موجود — وهو **مشتقّ**، فلا يجب أن يوجد كعمود |

**سابقة تسمية:** `InventoryTransfer.shipment_cost_cents Int?` — نفس الشكل ونفس الوحدة.

**ما تقرؤه التحليلات:** `SUM(o.delivery_fee_cents)` — أي **الإيراد فقط**. لا مكان في النظام يعرف كم دفع التاجر، فهامش الشحن كان غير قابل للحساب.

## 2. الحبيبية — القرار المهمّ

التكلفة تُفوتر **لكل شحنة**، والرسم يُحصَّل **لكل طلب**:

```
Order  (delivery_fee_cents — رسم واحد دفعه العميل)
  └── Fulfillment  (موقع)
        └── Shipment  ← فاتورة
        └── Shipment  ← فاتورة
```

```
netCharge  = delivery_fee_cents − cancelled_delivery_fee_cents
actualCost = SUM(shipment.actual_cost_cents)
subsidy    = max(0, actualCost − netCharge)
margin     = max(0, netCharge − actualCost)
```

**ثلاث نقاط مثبَّتة باختبارات:**

1. **الإلغاء يُخصم من الرسم** — رسم مُعاد للعميل مال لم يعد لدى المتجر؛ حسابه على الإجمالي يخترع ربحًا.
2. **الجمع على مستوى الطلب لا الشحنة** — طلب مقسّم = رسم واحد مقابل فاتورتين. المقارنة لكل شحنة تُظهر ربحًا على كلٍّ منهما.
3. **`max(0, …)` على الطرفين** — الدعم ليس ربحًا سالبًا والعكس؛ كلٌّ صفر حين ينطبق الآخر، فيمكن جمع أيّهما عبر الطلبات بلا إلغاء متبادل.

## 3. الـ schema delta

```prisma
model Shipment {
  /// ما فوتره الناقل مقابل هذه الشحنة، بالوحدة الصغرى وبعملة المتجر.
  /// NULL = غير معروف بعد ≠ صفر (كلّفت لا شيء).
  actual_cost_cents Int?

  /// provider | manual — هل قال الناقل هذا الرقم أم كتبه إنسان؟
  cost_source String?
}
```

| البند | التقييم |
|---|---|
| النوع | **إضافي** — عمودان nullable |
| `prisma db push` | ✅ يمرّ |
| Backfill | **لا شيء** — القائم يبقى `NULL` = «غير معروف»، وهو الصحيح |
| التراجع | إسقاط عمودين |

### ما استُبعد عمدًا

- **`Order.actual_shipping_cost_cents`** — تكرار مشتقّ يختلف أول مرة تُعدَّل شحنة. الجمع عند القراءة.
- **`Order.merchant_subsidy_cents`** — مشتقّ لا يُكتب.
- **عمود عملة للتكلفة** — نقطة التوسّع `actual_cost_currency`، موثّقة لا مبنيّة.
- **جدول فواتير شحن** — أبكر من الحاجة.

## 4. من يملأ التكلفة

**١. المزوّد وقت الحجز** — `ProviderShipment.costCents?` على واجهة PHASE 5. `manual` يُرجع `null` دائمًا ولا يخترع رقمًا.

**٢. التاجر بيده** — `setShipmentActualCost(id, cost_cents)` بـ `cost_source: 'manual'`.

> **وهذا سبب تقديم PHASE 7 على 6:** متجر `MERCHANT_MANAGED` دفع لسائق ويعرف كم دفع — فهامش الشحن يصير مرئيًّا **بلا أي ناقل حقيقي**.

---

## 5. الحماية — تكلفتنا ليست شأن العميل

`ShipmentEntry` و`OrderEntry` **يقرؤهما العميل أيضًا**. لذلك التكلفة والاقتصاديات تُحجب على مستوى الـ mapping بحسب دور القارئ، لا بحقل مكشوف. اختبارات تثبّت غيابها للعميل.

---

## 6. ما لا يتغيّر إطلاقًا

`selectShippingRule` و`computeShippingFeeCents` — ما يدفعه العميل يبقى قرار التاجر عبر مناطقه. **التكلفة لا تؤثّر على السعر بأي شكل.** الـ checkout بلا تغيير. `rate()` تبقى غير موصولة.

## 7. المخاطر

| # | الخطر | الحدّ منه |
|---|---|---|
| R1 🟠 | **`NULL` تُقرأ كصفر** فيظهر دعم = الرسم كامل | `is_complete` + استبعاد غير المكتمل من أي مجموع |
| R2 🟠 | **تسرّب التكلفة للعميل** | حجب على مستوى الـ mapping + اختبار |
| R3 🟡 | **عملة الناقل ≠ عملة المتجر** | مقبول اليوم؛ موثّق كنقطة توسّع |
| R4 🟡 | **رقم يدوي فوق رقم الناقل** | `cost_source` يميّزهما |
| R5 🟡 | **التكلفة تتسرّب إلى التسعير** | قاعدة موثّقة؛ للتسعير مستدعيان اثنان فقط |
