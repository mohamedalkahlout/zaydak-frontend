## الهدف

أن يظهر العطل المؤثر بسرعة لصاحب مسؤولية محدد، وأن تمنع بوابات الدمج والنشر تكرار الثغرات والأخطاء الأساسية، مع دليل يربط كل نتيجة بإصدار وبيئة.

العمل هنا يثبت تشغيل الميزات الحالية ضمن تجميد الإضافات؛ لا يبني منصة تحليلات أو نظام BI جديداً.

## المشكلة والأدلة

هذه قراءة لتهيئة المصدر؛ لم يُفحص Sentry أو تشغيل GitHub Actions أو حماية الفروع في الحسابات الحيّة.

| البند | الدليل وحدوده |
|---|---|
| إسقاط أخطاء تطبيقية | [sentry.ts](../../back-end/src/common/observability/sentry.ts) يستبعد كل error code لا يبدأ بـ`internal_`، بينما [enum الأخطاء](../../back-end/src/common/enums/error-codes.enum.ts) يستخدم رموزاً كبيرة مثل `INTERNAL_SERVER_ERROR`. إصلاح حالة الأحرف وحدها لا يصنف `DATABASE_ERROR` بصورة صحيحة. |
| المتجر العام يحتاج دمج مراقبة | البحث الحالي في [package.json للمتجر](../../apps/storefront/package.json) ومسارات ملفات المتجر لا يظهر دمج Sentry؛ التقرير §15 وملحق المتجر يسجلان الفجوة. يجب إثبات التقاط أخطاء server وbrowser بعد التنفيذ. |
| CI موجود وواسع | [ci.yml](../../.github/workflows/ci.yml) يشغّل backend types وDI وschema والوحدة وdrift، وfrontend codegen/lint/types/test/build ودخان vendor/admin. المحافظة على الموجود مطلوبة. |
| runtime e2e خارج البوابة الحالية | CI يشغّل `typecheck:e2e` و`test:concurrency` (على قاعدة بيانات CI بعد `db:deploy` والبذور، ويفشل إذا غاب `DATABASE_URL_TEST`)، لكنه لا يشغّل `test:e2e` ولا رحلة Playwright تجارية. فحص الأنواع ليس اختبار تنفيذ. (صُحّح 2026-09-22: كان هذا البند يقول إن `test:concurrency` لا يعمل في CI.) |
| lint الخلفي غير موجود في CI | [package.json الخلفي](../../back-end/package.json) يعرّف `lint` مع `--fix`؛ إضافته كما هو تجعل فحص CI يعدّل المصدر. |
| فحوص قد تنجح وهي skipped | [اختبارات concurrency](../../back-end/test/concurrency/README.md) تتطلب `DATABASE_URL_TEST`؛ إعداداتها ووثائق SQL تحتاج مواءمة مسار P03 قبل اعتماد نتيجة خضراء. |
| دخان الصفحات لا يثبت رحلة البيع | [smoke-routes.mjs](../../scripts/smoke-routes.mjs) وCI يفحصان render لمسارات محددة؛ لا يثبتان صحة الجلسة الحقيقية أو إنشاء طلب أو خصم مخزون أو الدفع. |

المرجع التاريخي: [تقرير الجاهزية](../investor-readiness-report-ar.md)، §8 و§15 وملحق البنية الداخلية. نتائج الاختبارات القديمة لا تمثل نتيجة التنفيذ لهذه المرحلة.

## الحل المعتمد

1. سياسة تصنيف أخطاء صريحة تشمل الخادم وقاعدة البيانات والاعتماديات، وتستبعد الخطأ المتوقع فقط بعد تحديده؛ تمرر الأخطاء غير المعروفة للتحقيق.
2. مراقبة التطبيقات الأربعة والعمال، مع release/environment وrequest/job ID وسياق محدود خالٍ من tokens وOTP ورسائل العملاء الخام.
3. قياس مؤشرات تشغيل قليلة مرتبطة بأثر واضح: أخطاء الطلبات والشراء، زمن الاستجابة، صحة DB/Redis، عمر وطول الطوابير وفشل التسليم والنسخ الاحتياطي.
4. بوابات CI منفصلة للـbackend وworkspaces، مع اختبارات تكامل تحتاج DB/Redis حقيقيتين في بيئة اختبار وخطأ صريح عند غياب شروط التشغيل.
5. P10 يملك محتوى رحلة البيع والتحميل الشاملة؛ هذه المرحلة تملك runner موثوقاً وبوابات واحتفاظاً بالأدلة، ثم تُربط رحلة P10 به قبل P11.

## النطاق والاستثناءات

- يشمل capture/errors والتصنيف والتنقيح والتنبيهات وrunbooks وحماية الدمج وربط النتيجة بالـcommit.
- يشمل جودة المصدر الحالية وschema/codegen drift والتكامل وسباقات البيانات واختبار failure paths الأساسية.
- P09 يملك تجربة error boundaries واستعادة الصفحة؛ P04 يملك وصول أحداثها للمراقبة دون تكرار الملكية.
- لا يشمل تعميم tracing عالي التكلفة أو اختبار كل شاشة في المتصفح؛ تحدد التغطية وفق مخاطر الإطلاق.

## المخرجات المطلوبة

- سياسة أخطاء واختبارات فلترة وتنقيح؛ وصول أحداث تحقق من كل تطبيق ومن عامل خلفي.
- dashboard محدودة بمؤشرات الإطلاق، وعتبات ومالكي استجابة وrunbooks مرتبطة بها.
- workflow محدث وrequired checks مثبتة بالإعداد الفعلي، مع fixtures وأدلة اختبارات غير skipped.
- تقرير تجربة عطل يربط commit والبيئة والحدث والتنبيه والزمن والإجراء ونتيجة الاستعادة.

## أوامر التحقق المرجعية

الأوامر التالية موجودة في المستودع ولم تُشغّل أثناء كتابة الخطة. تُنفذ بعد إعداد الاعتماديات وبيئة اختبار معزولة، وليست أوامر على الإنتاج.

```powershell
# من جذر المستودع: apps وpackages فقط
npx turbo run lint typecheck test --continue
npx turbo run build

# داخل back-end: تثبيت مستقل وPrisma client جاهز
npx eslint "{src,apps,libs,test}/**/*.ts"
npm run typecheck:all
npm run typecheck:e2e
npm run check:di
npm run schema:check
npm test -- --runInBand

# داخل back-end وبعد إعداد DB/Redis/fixtures المعزولة المطلوبة
npm run test:e2e -- --runInBand
npm run test:concurrency -- --runInBand
npm run check:drift
```

لا يُستخدم `npm run lint` الخلفي بوصفه فحصاً غير معدّل لأنه يحتوي `--fix`. ولا تُعتمد نتيجة e2e إذا غابت متغيرات الاختبار أو تجاوز runner الاختبارات؛ يُسجَّل العدد المنفذ فعلياً.

## سيناريوهات التحقق

| السيناريو | النتيجة المطلوبة |
|---|---|
| `INTERNAL_SERVER_ERROR` و`DATABASE_ERROR` وخطأ بلا code | يصل الحدث المقصود مع release وenvironment الصحيحين؛ لا يسقطه الفلتر. |
| validation متوقع أو رفض صلاحية اعتيادي | لا يصنع ضجيج أخطاء خادم؛ يبقى سجل الأمن المطلوب منفصلاً. |
| خطأ browser وخطأ server في المتجر | قابلان للتتبع إلى الإصدار الصحيح دون عرض بيانات حساسة للعميل. |
| payload يحوي token أو OTP أو بريد/نص خاص | الأدلة المنقّحة لا تحتوي الحقول المحظورة وفق سياسة P07. |
| Redis متوقف أو job تفشل مراراً | تنبيه يصل للمسؤول، ويربطه runbook بالإجراء مع منع تكرار الأثر. |
| حذف `DATABASE_URL_TEST` من job التكامل | تفشل البوابة برسالة إعداد؛ لا نجاح أخضر بسلسلة اختبارات skipped. |
| تغيير schema أو generated types دون مزامنة | يفشل check المناسب؛ تحديث codegen لا يخفي schema قديماً. |
| خطأ TypeScript في backend وfrontend | كلا job مستقل ويمنع الدمج؛ نجاح أحدهما لا يغطي الآخر. |
| فشل اختبار أمني متعمد في فرع تجربة | CI يفشل والـrequired check يمنع الدمج، ثم يزال التغيير التجريبي. |

- [ ] بوابات المصدر وschema/codegen/build الحالية محفوظة وrequired checks مفعّلة بالفعل.

## الاعتماديات والقرارات المفتوحة

- Sentry وCI يبدأان مبكراً؛ إغلاق P04 ينتظر بيئة P03 المستقرة وإثباتات P01/P02.
- P05/P06 يحددان ويضيفان assertions الخاصة بالأموال والمخزون بعد توفر بيئة P04؛ P10 يضيف الرحلات والأداء إلى CI القائم. النتائج الجديدة تلحق بأدلة P04 دون تحويل اعتمادها على الاختبارات اللاحقة إلى حلقة تمنع بدء التنفيذ.
- يلزم حسم قنوات التنبيه والعتبات والاحتفاظ والمالك البديل، وسياسة required checks وحالات الاستثناء الموثقة.

## التراجع والتعافي

- إذا سبب SDK أو tracing حملاً غير مقبول، يخفض sampling أو يعطل الجزء المسبب مع استمرار التقاط الأخطاء الأساسية.
- عند ضجيج تنبيهات، تعدل العتبات أو التصنيف بعد حفظ الدليل؛ لا يعاد فلتر يسقط كل أخطاء الخادم.
- خلل في runner يعالج مع حفظ نتيجة آخر commit موثوق؛ لا تزال بوابة أمن أو بيانات لإجازة إصدار فاشل.
