# P10 — الأداء والتحقق الكامل على نسخة الإصدار

| الحقل | القيمة |
|---|---|
| الحالة | لم تبدأ |
| تاريخ إعداد الخطة | 2026-09-16 |
| المسؤول | قائد الجودة، بمشاركة قادة الـBack-end والواجهات والتشغيل |
| الاعتماديات | يمكن تجهيز harness بعد P03/P04؛ القبول النهائي يعتمد على P01–P09 كلها |
| بوابة الخروج | رحلات وحسابات وعزل وأداء مثبتة باختبارات قابلة للإعادة على SHA الإصدار المرشح |

## الهدف

إثبات أن الإصدار يعمل من المتصفح إلى الـAPI إلى PostgreSQL وRedis والعمال الخلفيين، ويحافظ على صحة المال والعزل تحت التزامن وحجم البيانات المتوقع.
تُحدد حدود التشغيل من قياس بيئة مماثلة للإنتاج، وتُحفظ أدلة يمكن لشخص آخر إعادة إنتاجها قبل الانتقال إلى بوابة الإطلاق P11.
لا يشمل هذا الملف تشغيل اختبارات حالياً؛ الحالة «لم تبدأ» تبقى حتى تنفيذ المهام وتسجيل نتائج فعلية.

هذه مراجعة بنيوية للمصادر، وليست نتيجة تشغيل اليوم. يلزم جرد الحالات المنفذة/المتخطاة على SHA الاختبار قبل اعتماد أي تغطية.

## الحل المعتمد

1. بيئة اختبار معزولة ببيانات تركيبية، build إنتاجي للتطبيقات الثلاثة، وAPI وPostgreSQL وRedis حقيقية.
2. سيناريوهات محددة تقيس الأثر في البيانات والسجلات، لا مجرد ظهور toast أو HTTP 200.
3. اختبارات تكامل حتمية تستخدم sandbox/adapter مضبوطاً للمزوّد الخارجي، مع smoke فعلي منفصل للتكاملات المفعّلة من P08.
4. تشغيل التزامن ضد قاعدة البيانات الحقيقية لإثبات الأقفال والقيود والمعاملات والتسوية مرة واحدة.
5. قياس الأداء قبل التغيير وبعده على dataset وموارد وحمل ثابتة؛ لا تحسين بلا bottleneck مقاس.
6. تقرير إصدار واحد يسجل SHA والبيئة والأوامر والـartifacts والـskips والفشل وحدود الاستنتاج.

## النطاق وما يؤجّل

- ضمن النطاق: تجارة وهوية وعزل وصلاحيات، استعادة الوظائف، البحث والتحليلات، الواجهات الأساسية، ومراقبة موارد API والعمال.
- لا تتصل اختبارات الحمل ببيانات الإنتاج ولا ترسل طلبات أو رسائل مدفوعة دون خطة تشغيل معتمدة؛ المزود الحقيقي له smoke صغير منفصل.
- يُستبعد تحسين كل شاشة، بناء محرك بحث جديد تلقائياً، أو تحقيق 100 في Lighthouse كشرط للإطلاق.
- لا يؤجّل اختبار سلامة المال أو عبور المتاجر؛ القدرات الاختيارية تستبعد فقط بعد تعطيلها في الخادم والواجهة واعتماد نطاقها.

## مهام التنفيذ بالترتيب

- [ ] **P10-T01 — جرد الوضع.** سجل كل suite وهدفها وبيئتها وما إذا كانت تنفذ assertions أو تتخطى/تحتوي TODO؛ ميّز typecheck وunit وintegration وbrowser وprovider smoke.
- [ ] **P10-T02 — تثبيت fixture.** أنشئ متجري A/B لمالك واحد ومتجر C لمالك آخر، عملاء وأدوار محدودة، منتجات وأسعار ومخزون وكوبونات وطلبات تركيبية مع seed قابل للإعادة.
- [ ] **P10-T03 — حواجز قاعدة الاختبار.** استخدم DB/Redis مستقلين واسم بيئة صريحاً؛ افشل الإعداد إن أشار إلى remote production أو غابت متطلبات suite؛ لا يعتبر skip أخضر في بوابة الإصدار.
- [ ] **P10-T04 — runner للإصدار.** ثبّت تبعية Playwright المباشرة والـlockfile والمتصفحات إن لم تكن مثبتة صراحة؛ أضف إعداداً للإصدار يحافظ على suite تخطيط composer الحالية.
- [ ] **P10-T05 — تشغيل متكامل.** ابنِ وشغّل API والتطبيقات الثلاثة وworkers، انتظر readiness ثم نفّذ الدخول من النماذج الحقيقية؛ خصص بيانات مستقلة لكل worker اختبار متوازٍ.
- [ ] **P10-T06 — lifecycle حقيقي.** أكمل إنشاء الطلب والدفع/التأكيد والشحن والإلغاء والاسترداد الكامل والجزئي والرصيد والمخزون؛ تحقق من قيود DB والledger بعد كل خطوة.
- [ ] **P10-T07 — حالات الأموال السلبية.** اختبر مجموع غير صحيح، عملة خاطئة، دفع فشل/تأخر، webhook خاطئ/مكرر/متأخر، وإعادة تحميل الصفحة بعد إنشاء الطلب؛ لا كتابة مالية مضاعفة.
- [ ] **P10-T08 — التزامن.** نفّذ سباق آخر وحدة مخزون، آخر استخدام كوبون عام/لكل عميل، اعتماد refund مرتين، سحب متزامن، وآخر وحدة حصة AI؛ افحص rollback بعد فشل وسط المعاملة.
- [ ] **P10-T09 — حدود المستأجرين.** غيّر X-SHOP والـhost وIDs والكوكي بين A/B/C؛ جرّب GraphQL وREST/SSE وwebhooks والعمال والبحث والكاش مع حسابات الأدوار المختلفة.
- [ ] **P10-T10 — الهويات والجلسات.** أثبت رفض signup token كرمز دخول، invalid/expired/revoked tokens، refresh المتزامن، تغيير الدور، وفصل حساب/متجر سابق من cache الواجهة.
- [ ] **P10-T11 — رحلات المتصفح.** آلياً نفّذ مصفوفة P09 بالعربية/الإنجليزية والهاتف/سطح المكتب، وpath/subdomain/custom domain المفعّل؛ أي تحويل login غير متوقع يفشل الاختبار.
- [ ] **P10-T12 — تعطل الخدمات.** اختبر timeout للمزوّد وRedis، توقف worker وإعادته، redelivery بعد crash، وتغيير ترتيب الأحداث؛ أثبت حالة مفهومة وتعافياً وعدم فقد/تكرار الأثر.
- [ ] **P10-T13 — خطة الحمل.** اعتمد حجم الكتالوج والطلبات والتجار النشطين ومزيج read/write ومدة الحمل ودرجة التزامن مع P00/P03؛ سجّل نسخة البيانات وموارد الجهاز والمنطقة.
- [ ] **P10-T14 — baseline.** قِس p50/p95/p99 والأخطاء وthroughput، زمن DB واتصالاتها، heap/RSS وevent-loop lag، أوامر Redis، عمق/عمر الطابور وتكلفة الطلب.
- [ ] **P10-T15 — البحث.** التقط `EXPLAIN (ANALYZE, BUFFERS)` في بيئة الاختبار لاستعلامات واقعية؛ قِس JSONB/وسوم/تطبيع العربية؛ اختر فهرساً أو عمود بحث/تجميعاً مناسباً بناء على الخطة وأثبت صحة النتائج والعزل.
- [ ] **P10-T16 — التحليلات.** انقل التجميعات الكبيرة إلى SQL مع حدود الزمن والمخرجات والفهارس؛ طابق النتائج مع dataset مرجعي للمرتجعات والعملات والمناطق الزمنية والطلبات parent/child.
- [ ] **P10-T17 — API والعمال.** قارن حالة idle والذروة مع imports/AI/notifications تعمل؛ نفّذ فصل/تقييد العمال المعتمد في P03 إذا أثبت القياس التنافس؛ احفظ budgets لكل pool واتصالاته.
- [ ] **P10-T18 — واجهات الإنتاج.** قِس تحميل كتالوج/منتج وشراء ولوحات أساسية بذاكرة باردة ودافئة؛ راجع الصور وJavaScript وطلبات البيانات وتسلسلها والـlayout shifts على هاتف ممثل.
- [ ] **P10-T19 — تحسين موجّه.** أصلح أكبر أسباب تجاوز الحدود فقط، وأعد السيناريو المتأثر؛ لا ترفع سقف الاختبار لتغطية تراجع غير مفسر ولا تخفف شروط صحة المال والعزل.
- [ ] **P10-T20 — CI موثوق.** صِل integration/browser smoke بالـCI مع PostgreSQL/Redis وbuild إنتاجي، readiness وتنظيف البيانات والـartifacts؛ أي حالة حاجبة skipped/todo أو فشل setup يفشل job.
- [ ] **P10-T21 — تشغيل الإصدار.** شغّل بوابة الرحلات والحمل والمصالحة على SHA مرشح واحد بعد إغلاق P01–P09؛ وثّق أي flaky case وأصلحه بدلاً من إخفائه بإعادة محاولات غير محدودة.
- [ ] **P10-T22 — حزمة القرار.** أرفق الأوامر والنتائج والـtraces وخطط SQL ومقارنة قبل/بعد والحدود المعتمدة؛ سلّم P11 قائمة عيوب مفتوحة مصنفة وقرار كل استثناء مسموح.

## حدود القياس المقترحة — تحتاج اعتماداً

الأرقام التالية نقطة بدء للتفاوض، وليست قياسات حالية أو SLA أو موافقة مسبقة. يعتمدها مالك المنتج والتشغيل قبل الحمل في P10-T13، أو يحدد بدائل مع سبب وموارد وحجم بيانات واضحين.

| القياس | حد مقترح أولي | طريقة الإثبات |
|---|---|---|
| بحث وقراءة API الأساسية | p95 ≤ 800ms عند الحمل المعتمد | من مولد حمل في منطقة معلومة؛ زمن الشبكة وDB ظاهر |
| إنشاء الطلب الداخلي | p95 ≤ 1500ms دون زمن المزوّد الخارجي | قياس منفصل للزمن الكلي ولوقت خدمة الطلب داخلياً |
| أخطاء الخدمة غير المتوقعة | أقل من 1%؛ صفر مخالفة مالية أو عزل | افصل 4xx المتوقعة عن 5xx وtimeouts |
| فترة الثبات | 30 دقيقة بعد warm-up، ثم burst قصير موثّق | لا نمو ذاكرة مستمر ولا نفاد pool ولا فقد وظائف |
| تأخر وظيفة أساسية | p95 ≤ 60 ثانية ضمن حملها المعتمد | زمن انتظار الطابور منفصل عن زمن التنفيذ وتسليم المزوّد |
| Storefront | LCP ≤ 2.5s، INP ≤ 200ms، CLS ≤ 0.1 | هدف ميداني p75؛ اختبارات المختبر قبل الإطلاق مؤشر أولي فقط |

حدود Core Web Vitals من [مرجع web.dev](https://web.dev/articles/vitals). لا يوجد جمهور ميداني كافٍ قبل الإطلاق، لذلك تُسجّل فجوة field data وتبدأ مراقبتها في P11؛ نتيجة Lighthouse واحدة لا تثبت INP ميدانياً.
تُراجع الأرقام مع شريحة الهاتف والشبكة وحجم الكتالوج المختارين، وتظل صحة المال والعزل شرطاً مطلقاً عند أي مستوى حمل.

مرجع إعداد المتصفحات والاعتماديات في CI: [Playwright الرسمي](https://playwright.dev/docs/ci)، روجع 2026-09-16؛ تطبق التعليمات بما يطابق إصدار المستودع المثبت.

## سيناريوهات التحقق الحاسمة

| السيناريو | الإثبات المطلوب |
|---|---|
| N عملاء يشترون آخر وحدة | عدد النجاحات مطابق للمخزون، لا رصيد سالب ولا أثر مالي لفاشل |
| refund/webhook/job يصل مرتين | انتقال واحد وقيود دفتر/مخزون/حصة واحدة حسب نوع العملية |
| طلب يفشل بعد حجز كوبون أو مخزون | rollback كامل أو تعويض موثّق؛ لا مورد عالق |
| استعلام بحث وتحليلات على dataset كبير | نتائج مطابقة وموارد ضمن الحدود المعتمدة؛ لا عبور للمتاجر |
| worker مشغول بالاستيراد أثناء checkout | زمن API قابل للقبول، ولا استنزاف لقاعدة البيانات أو Redis |
| بناء إنتاجي للتطبيقات الثلاثة | render فعلي لكل رحلة دون خطأ console أو login redirect مضلل |
| إعادة التشغيل على SHA نفسه | النتيجة قابلة للإعادة، والبيانات والتهيئة والأوامر معروفة |

## المخرجات ومعايير القبول

- [ ] harness موثّق يعمل من إعداد نظيف ببيانات معزولة؛ المتطلبات المفقودة تفشل ولا تتخطى الاختبارات الحاجبة بصمت.
- [ ] تقرير P01–P09 مغلق أو يحدد قدرات اختيارية معطّلة بقرار نطاق؛ لا ثغرة مال/هوية/عزل مؤجلة كتحسين.
- [ ] التجارة والتزامن والهوية والعزل اجتازت DB/Redis حقيقيين؛ يوجد smoke فعلي لكل مزوّد مفعّل وفق P08.
- [ ] مصفوفة المتصفح تجتاز التطبيقات الثلاثة والأجهزة واللغات وأنماط النطاق المفعّلة على build إنتاجي.
- [ ] حدود الحمل اعتمدت قبل القياس، وسجّلت dataset وموارد API/workers/pools والنتائج والمشكلات المتبقية.
- [ ] البحث والتحليلات يحافظان على صحة النتائج مع حمل ممثل؛ توجد مقارنة SQL وموارد قبل/بعد عند التغيير.
- [ ] CI ينفذ الاختبارات ولا يكتفي بتجميعها؛ الحالات الحاجبة لا تحمل skip/todo ولا flaky معروفاً بلا معالجة.
- [ ] حزمة أدلة واحدة مرتبطة بـSHA الإصدار وأوامر قابلة للإعادة؛ أي إصلاح لاحق يحدّث SHA ويعيد البوابات المتأثرة والرحلات الأساسية.

## الاعتماديات والقرارات المفتوحة

- P03 يحدد البنية وبيئة staging والنسخ الاحتياطي؛ P04 يحدد جمع القياسات وتنقيح artifacts؛ P00 يعتمد حجم الإطلاق.
- مالك كل مرحلة يصحح سبب فشل اختبارها؛ P10 لا يغير قواعد المال أو الصلاحيات لتسهيل النجاح.
- تُحسم ميزانية provider smoke وسقف البيانات ومدة الحمل ومعيار قبول العيوب البصرية قبل التشغيل؛ الأسرار ومعلومات العملاء لا تُرفق بالتقارير.

## الرجوع عند التعثر

أوقف مولد الحمل عند خرق عزل/مال أو استنزاف موارد، واحفظ الأدلة ثم أصلح البيئة/الإصدار في المرحلة المالكة.
اختبارات التنظيف تمس قاعدة الاختبار المثبتة فقط؛ migrations والفهارس الجديدة ترجع وفق خطة P03 وليس بحذف عشوائي للبيانات.
إذا تعذر تحقيق الحد المقترح، يُبحث تقليل حجم الإطلاق أو ضبط الموارد بقرار مالك موثّق وإعادة قياس؛ لا يُعدّل تقرير النجاح بأثر رجعي.
