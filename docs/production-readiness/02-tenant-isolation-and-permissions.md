## الهدف

ألا يستطيع مستخدم قراءة أو تعديل أو تصدير أو بث بيانات متجر آخر بتغيير `X-SHOP` أو معرّف مورد؛ وأن يظل وصول الإدارة مقيداً بصلاحية صريحة ومسجلاً.

المطلوب إغلاق حدود الثقة الحالية ضمن تجميد الميزات، دون بناء نظام موظفين وأدوار جديد خارج نطاق الإطلاق.

## المشكلة والأدلة

المراجعة التالية قراءة مصدر بتاريخ الخطة؛ غياب اسم حارس وحده لا يثبت ثغرة، فقد توجد حماية داخل الخدمة. الحكم النهائي لكل عملية يحتاج تتبعاً واختباراً.

| البند | الدليل وحدوده |
|---|---|
| صلاحية على الصنف قد لا تُقرأ | [PermissionsGuard](../../back-end/src/auth/guards/permissions.guard.ts) يقرأ metadata للدالة فقط، بينما decorator يدعم الصنف أيضاً؛ [AdminShopDomainsResolver](../../back-end/src/shop-domains/admin-shop-domains.resolver.ts) من الأسطح المطلوب التحقق منها. |
| موارد تُقرأ بالمعرّف وحده | [SavedPromptsService](../../back-end/src/saved-prompts/saved-prompts.service.ts) يحمل `findOne(id)` وتحديثاً وحذفاً بالمعرّف دون شرط ملكية في تلك الاستعلامات. |
| أسئلة وFAQ | [QuestionsResolver](../../back-end/src/questions/questions.resolver.ts) و[FAQsResolver](../../back-end/src/faqs/faqs.resolver.ts) لا يحملان إثبات ملكية واضحاً في سلاسل حراس الكتابة المقروءة؛ يلزم تتبع خدماتهما. |
| بيانات تنبيهات المخزون | [StockNotificationsResolver](../../back-end/src/stock-notifications/stock-notifications.resolver.ts) يحمي `pendingStockNotifications` بـJWT فقط؛ يجب إثبات تفويض قراءة بيانات المشتركين. |
| بث وكيل التاجر | [VendorAgentController](../../back-end/src/vendor-agent/vendor-agent.controller.ts) يطبق صلاحية ونطاق متجر دون `ShopOwnershipGuard` في نقاط البث الثلاث؛ ملكية المتجر والمحادثة تحتاجان اختباراً مستقلاً. |
| تصدير CSV | [CustomerSegmentsController](../../back-end/src/customer-segments/customer-segments.controller.ts) يمرر `x-shop` الخام إلى خدمة التصدير دون سلسلة حراس النطاق. التعليق الذي يعد بالملكية لا يثبتها. |
| تغيير صلاحيات الدور | [RolePermissionsService](../../back-end/src/role-permissions/role-permissions.service.ts) يستبدل مصفوفة صلاحيات مستخدمي الدور عبر `updateMany`؛ لا يظهر فيه تدقيق أو إبطال جلسات. |
| الطلبات والفوترة وسياسات الإرجاع | [التقرير](../investor-readiness-report-ar.md) §5 و§6 يذكر خلط منتجات متاجر مختلفة وعمليات فوترة وسياسات إرجاع؛ تُعامل كبنود واجبة إعادة الإثبات، لا كاختبارات منجزة في هذه الخطة. |

أعداد مثل «63 resolver» و«68 عملية» في التقرير نقاط بداية للجرد وليست عدّاً حديثاً أو قائمة نهائية للثغرات.

## الحل المعتمد

1. جرد كل عملية منشورة وتصنيفها: عامة، خاصة بالمستخدم، خاصة بمتجر، أو إدارة منصة. يحدد الجرد الحارس وشروط الخدمة والنتيجة المسموحة.
2. فصل ثلاثة أسئلة: من المستخدم؟ ما المتجر المطلوب؟ هل يملك حق هذا الإجراء على هذا المورد داخل المتجر؟ لا تجيب `X-SHOP` وحدها عن السؤال الثالث.
3. تمرير scope موثوق إلى الخدمات، وربط الاستعلام بالمتجر أو المستخدم عند قراءة المورد وتحديثه؛ تجنب فحص منفصل ثم كتابة غير مقيّدة.
4. توحيد دلالة صلاحيات الصنف والدالة، مع قرار واضح هل الدالة تستبدل شرط الصنف أو تضيف إليه، والحفاظ على دلالة «أي صلاحية» الحالية إلا بتغيير مقصود.
5. فصل منح الدور عن الاستثناءات الفردية عند تحديثهما أو استخدام تحويل يحافظ عليها؛ إبطال الجلسات المتأثرة وسجل تدقيق قابل للمراجعة.

## النطاق والاستثناءات

- يشمل GraphQL وREST وSSE والتصدير والوظائف الخلفية التي تستقبل معرّفات متجر أو مورد من المستخدم.
- يشمل الطلبات والفوترة وFAQ والأسئلة والمحفوظات وبيانات المشتركين وسياسات الإرجاع والمحادثات ومجالات الإدارة.
- يشمل الموارد المحذوفة منطقياً والمتاجر المعلقة أو المحذوفة ونطاق جلسات المتجر العام.
- يستثني بناء ShopMembership أو أدوار موظفين متعددة؛ لا يستخدم هذا الاستثناء لتبرير الوصول العابر بين المالكين الحاليين.
- سلامة الحسابات المالية في P06، وصحة التسعير والمخزون في P05؛ هذه المرحلة تملك منع الوصول غير المصرح.

## المخرجات المطلوبة

- مصفوفة تفويض كاملة ومراجعة، مرتبطة بملفات المصدر واختبارات كل سطح.
- إصلاحات الحراس والخدمات دون تغيير عرضي للمسارات العامة أو إدارة المنصة.
- سجل استثناءات إدارية يشرح الصلاحية والنطاق والتدقيق المطلوب.
- تقرير حالات رفض يثبت عدم حدوث آثار جانبية، وتقرير مسارات نجاح للتاجر الصحيح والإدارة المفوضة.

## سيناريوهات التحقق

| السيناريو | النتيجة المطلوبة |
|---|---|
| مالك A يرسل `X-SHOP=B` مع مورد B | رفض قبل إرجاع البيانات أو الكتابة أو إنشاء job. |
| مالك A يرسل `X-SHOP=A` مع مورد B | رفض؛ قيد الخدمة يمنع تجاوز حارس الترويسة. |
| عميل يمرر معرّف متجر إلى عملية إدارية | رفض حتى إن كان JWT صحيحاً والصلاحية على مستوى الصنف. |
| طلب متجر A يحتوي نسخة منتج من B | رفض العملية كاملة؛ لا طلب جزئي ولا خصم مخزون من أي متجر. |
| تبديل conversation في stream أو resume | رفض قبل أول محتوى أو استئناف أداة؛ لا تسرب تاريخ المحادثة. |
| معرّف محفوظة أو FAQ أو refund policy من متجر آخر | لا قراءة ولا تعديل ولا حذف؛ تحقق من الصف بعد الطلب. |
| تصدير شريحة بمتجر غير مملوك | لا ترويسة ملف أو سجلات CSV حساسة تتسرب. |
| إزالة صلاحية من دور مع وجود grant فردي | النتيجة تطابق السياسة المعتمدة، مع audit وإبطال الجلسة عند سحب صلاحية فعلية. |
| متجر معلّق أو مورد محذوف منطقياً | لا وصول عبر معرف قديم؛ تدعم رسائل الخطأ سياسة عدم كشف وجود المورد. |
| زيارة كتالوج عام وإدارة مفوضة | نجاح المسار المشروع؛ لا يكسر الإصلاح القراءة العامة أو الوصول الإداري المعتمد. |

- [x] صلاحيات الصنف والدالة تعمل وفق العقد الموثق، والوصول الإداري مسجّل.
- [x] تعديل صلاحيات الدور لا يمحو grants فردية دون قرار مقصود ومسجل، والإبطال مثبت.
- [ ] المراجع المستقل راجع الخدمات أيضاً؛ مجرد إضافة `ShopOwnershipGuard` لا يغلق المرحلة.

## الاعتماديات والقرارات المفتوحة

- P01 يحدد مصدر الهوية الموثوق والإبطال؛ يمكن جرد الأسطح أثناء إصلاحه.
- P00 يحسم هل الإطلاق متجر مستقل لكل checkout أو سوق متعدد المتاجر؛ نموذج الطلب يجب أن يطابقه صراحة.
- دلالة صلاحيات الصنف والدالة نُفّذت في T02؛ سياسة المنح الفردي عند تحديث الدور هي D29 (T08).
- P05/P06/P08 تستخدم fixtures واختبارات الحدود هنا؛ لا تكرر ملكية نفس الإصلاح عبر مراحل مختلفة.

## التراجع والتعافي

- عند كسر مسار مشروع، يصحح شرط النطاق أو يعطل المسار مؤقتاً؛ لا تزال حراسة الملكية لاستعادة الخدمة.
- تغييرات نموذج الصلاحيات تبدأ بنسخة snapshot للمنح الحالية وخطة تحويل قابلة للمراجعة؛ الاستعادة تحفظ سجل التدقيق.
- إذا اكتُشف وصول سابق عابر للمتاجر، يفتح حادث مستقل لحصر الأثر بالتنسيق مع P07 دون نسخ بيانات حساسة إلى هذا الملف.
