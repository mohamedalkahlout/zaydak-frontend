Scope: the open `TODO.md` follow-up under “X-SHOP names a shop; it does not
prove you own it”, plus the paid-card cancellation, disputed unapplied payment,
and reviewed re-import photo tasks. Base revision: `a17c2f64`, with this pass's

## Confirmed findings addressed

- **Chat confirmation crossed a shop/channel boundary.** The current-action
  pointer was keyed only by user. A WhatsApp reply could answer that account's
  Telegram card or a card staged for another shop. Pointers now include user,
  shop and channel; `ChatActionRunner.press` verifies all three against the
  current link, and rechecks shop ownership before executing. A WhatsApp link
  with a removed or foreign shop stops before reading a pending action.
  Consuming an old token only clears the current pointer if it still names
  that token. Legacy account-only pointers expire without being used.
- **Stripe could process the same event concurrently.** A duplicate with a
  `pending` claim used to run again, and two retries of a `failed` event could
  both claim it. Pending events now return duplicate; retry uses a conditional
  `failed` → `pending` update, and only its winner runs side effects.
- **Carrier retries had the same failed-event race.** Shipping webhooks now
  claim a failed event with one conditional update scoped to provider and
  authenticated account/event ID. Concurrent losing retries do not apply the
  shipment event again.
- **Manual cancellation could strand an accepted card payment.** Both
  `cancelOrder` and the cancellation/failure path in `updateOrder` now apply
  the existing refund-first rule to admins as well as merchants, under the
  order lock. A disputed or unapplied payment remains a separate state.
- **A dispute could debit funds the shop had not received.** New holds require
  an applied, completed intent without mismatch/duplicate flags. The dispute's
  own ledger entry proves the amount and currency to release or forfeit.
  Processing is serialized per dispute, with payment classification read
  under the order lock. A replay must not move the same held funds twice.
  Review caught and fixed a regression in late association: a final dispute
  may still acquire its missing order/shop IDs without reopening or moving funds.
- **Reviewed photo removal was lost on re-import.** Explicit image drops now
  carry internal replacement intent into the CSV writer. Empty primary,
  gallery and variant slots clear existing photos in the product transaction.
  An ordinary blank CSV cell still preserves existing media, and preview
  writes nothing.

## Boundaries inspected without a new ownership finding

| Surface | Evidence in the current code |
|---|---|
| Coupon product, buy/get product, collection, customer and segment IDs | `CouponsService.create` and `update` validate references against the coupon's shop; segment and collection reads also exclude deleted rows. |
| Image generation reference attachments | `ImageGenService.resolveReferenceUrl` requires attachment ID + shop ID + non-deleted row before resolving the reference. |
| Carrier pickup location IDs | `CarrierPickupService` reads each location with its shop ID before registering or updating upstream. |
| Stripe inbound authentication | `StripeService.constructWebhookEvent` requires the configured webhook secret and delegates raw-body signature verification to the Stripe SDK. |
| Carrier inbound authentication and authorization | The addressed enabled carrier account supplies the secret; the shipment lookup is constrained to that account; event dedupe is account-scoped. |
| WhatsApp and Telegram inbound authentication | Secrets are selected by the path's instance/bot identity, decrypted with row-bound context and compared in constant time before dispatch. |
| Replicate inbound authentication | The raw body is verified with HMAC and a timestamp window before prediction lookup/application. |
| Upload from URL | `AttachmentsService.fetchRemote` uses `safeFetch`: public addresses, pinned connection, per-hop checks, bounded body/time and file-signature validation. |
| Store-import requests | `createGuardedFetch` revalidates each request/redirect and pins the socket to the validated addresses; source URL validation alone is not the network boundary. |

These are source reviews plus local regression checks, not an external
penetration test or a live-provider walk.

## Continuation: linked account eligibility and identity services

The verified handset link previously survived suspension, account deletion
and removal of `manage_own_shop`. Both link resolvers now re-read the account
through `hasVendorAgentAccess` before routing a message or callback. A revoked
account resolves as unlinked. WhatsApp enrollment and spending a Telegram
pairing token check the same rule. `ChatActionRunner.press` rechecks it before
a form write or approval resume, alongside its existing scope and ownership
checks. A role name does not override a missing permission. This does not
retroactively cancel a tool already running when access is revoked.

The remaining `CartClaimService` responsibility was split as requested in the
backlog. `ChannelIdentityService` owns channel registration and thread binding;
the existing `CustomerIdentityService` owns per-shop customer resolution;
`CartMergeService` owns preserving guest-cart adoption. The storefront's
`CartSyncService` keeps its separate replacement policy. All internal callers
and Nest providers/exports were switched; no compatibility facade, migration
or data write was introduced. Registration and cart behavior tests moved with
their services, preserving the original assertions.

The account checks passed 9 suites / 154 tests, including a revoked verified
link, a stale pairing token and pending form/graph cards on both channels.
Cart, identity and chat regression checks passed across their final runs;
stale test fixtures for
